于是我将逻辑内置进入“每次”出手之后更新状态，在实现过程中我顺手修掉了一份数据一个原本一个副本的冗余，但是在实现排序的时候我遇到了新的问题：假设参与方有a、b，我要比较a.speed，b.speed（此处在构造函数处有定义，可以直接访问），现在外部传入一个firstMoverId，那么我应该怎么设计先手逻辑呢？此处firstMoverId用于解决同速比较时的裁决，因此就会产生四种可能，此处我采用std::sort作为比较器这里放一个签名：

```cpp
std::sort(vec.begin(),vec.end(),[this](long long a,long long b))
```

其中传入的三个参数分别是：起始点、终止点、排序规则。在比大小时，第三参可以使用默认参数进行升序排序，也可以调用std::greater进行降序排序——是 `<functional>` 头文件中的降序比较器仿函数。这个函数在每一次初始化stepRound后开始，对已经进入对局初始化的成员进行的排序，但是如何进入，即从：无序的参与者到无序的存活者数组，到有序的存活者数组，到初始化并进行一次对局，到锁定敌对阵营，然后出清死亡单位，循环至满足任一退出条件。上面所述，是给整个存活者排序，而索敌的时候，我也用到了这个逻辑，虽然我出错了，但是很有意思，以下是我的初版：
```cpp
if (!order_.empty())
{
    std::size_t slow = 0;

    for (std::size_t fast = 1; fast < order_.size(); ++fast)
    {
        auto slow_hp = units_.at(order_[slow]).HP;
        auto fast_hp = units_.at(order_[fast]).HP;

        bool i = (slow_hp > 0) ? true : false;
        bool j = (fast_hp > 0) ? true : false;

        if (i == true && j == true)
        {
            ++slow;
        }
        else if (i == true && j == false)
        {
            ++slow;
        }
        else if (i == false && j == true)
        {
            std::swap(order_[slow], order_[fast]);
            ++slow; // 交换后，这一格已经确认是活人
        }
        else
        {
            // 两者都死：slow 留住空位，fast 继续往后找
        }
    }

    // 循环结束后，slow 所在的最后一格还需要确认
    if (units_.at(order_[slow]).HP > 0)
        order_.resize(slow + 1);
    else
        order_.resize(slow);
}
```

这个出清的搜索器很重，使用了双指针法遍历，实现的效果是将所有死亡的单位排序到整个“参与者”数组的末尾，而事实上，这已经相当于“存活者”数组了，只取决于你怎么读。当然最简单的方法是在已有的数组中，由于速度目前没有任何机制能够改变初始状态，因此维护一个随时更新排序的数组显然不如使用能够跳过指定条件的指针，由此实现识别死亡单位。因此构造就会简单很多，这一步没有绝对的对错，如果之后要维护随时动态更改的 ，或者涉及三方阵营之上的，就会引入三个指针，这时候，我的双指针遍历完成一次排序，只需要弹出前三个即可。（如果这里的bool类型改成int类型将true/false隐式转换成1/0，倒是跟真值表有点像。）总之，引用我的学习日志中ds的一句：“双指针的合理用法是‘两方有序列表归并’（速度排序 + 同速裁决），但 4 个元素直接 std::sort 更简单”。


时不时地，跟我开玩笑似的，我在if-else结构反复踩坑，首先就是退出时机以及continue和空结构，一般在算法题中，对于每个判断条件都会有返回值去给调用的函数，或者退出运行，但是我在实际编写过程中经常提前在循环中退出，以下是我的旧版：
```cpp
void Battle::step()
{
    if (finished())
        return; // 这里符合意图：战斗结束，整次行动退出
    const auto actorId = currentActorId();
    const auto actorTeam = units_.at(actorId).team;
    std::vector<long long> candidates;
    for (const auto& [id, u] : units_)
    {
        if (u.team == actorTeam)
            return; // 错误：整个 step() 结束
        candidates.push_back(id);
    }
    // ……选目标、执行攻击……
    ++cursor_; // 遇到己方提前返回后，这里不会执行
}
```

修复之后如下：

```cpp
void Battle::step()
{
    if (finished())
        return;

    const auto actorId = currentActorId();
    const auto actorTeam = units_.at(actorId).team;
    std::vector<long long> candidates;

    for (const auto& [id, u] : units_)
    {
        if (u.team == actorTeam || u.HP <= 0)
	        continue; // 结束本次循环，继续检查下一个单位
        candidates.push_back(id);
    }
    // ……选目标、执行攻击……
    ++cursor_;
}
```

可能是思维惯性使然，退出循环的方法永远只会退出码或者空退出（return 0; return;），（Os：力扣你害惨了我！！！看懂的人都去力扣刷100道动态规划助助兴去了，LOL）

---

在上面，我把 Lambda 作为第三个参数传给 `std::sort`，其中的 `[this]` 用于捕获当前对象的指针。

例如在 `Battle::startRound()` 中，我直接写 `units_`，可以理解为省略了 `this->`，访问的是当前这场对局保存的单位数据。`this` 是指向当前对象的指针，`*this` 则是它指向的对象。

Lambda 会生成一个独立的函数对象。我在这里写 `[this]`，让它能够访问当前对局的 `units_`、`firstMoverId_`，据此比较两个单位的出手顺序。捕获之后，内部直接写 `units_` 就可以，也可以写成 `this->units_`。

这里还要注意对象的存活时间。`[this]` 保存了地址，原来的对象销毁之后，通过这个地址访问成员就会出问题。我目前把 Lambda 直接交给 `std::sort`，排序在这次调用中完成，期间当前对象还在。如果以后把它存起来，留到其他时候执行，就得确认那时的 `Battle` 对象是否还存在。

这也能接上我前面提到的“原件和副本”问题：

```
auto& self = *this; // 引用当前对象
auto self = *this;  // 复制当前对象
```

两行只差一个 `&`。通过第一行的 `self` 修改成员，改动会落在当前对象上；第二行得到了一份副本，修改它，原来的对局不会跟着变化。我之前已经在 `auto` 上踩过一次坑，到了这里，还是得看清楚自己拿到的到底是哪一份数据。
