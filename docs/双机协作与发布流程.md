# 双机协作与发布流程（macOS + Windows）

场景：同一个 Obsidian 库要在 Mac 和 Windows 两台机器上编辑，改动要同步，
但**不能**顺带把线上博客改掉。

---

## 一、先认清「什么操作会让线上博客变」

仓库里三条 GitHub Actions，触发条件都是同一句 `on: push: branches: [main]`：

| 工作流 | 触发条件 | 效果 |
|---|---|---|
| `.github/workflows/deploy.yml` | push 到 `main`，**无 paths 过滤** | Hexo 全站重建 → `rsync --delete` 到 `/var/www/blog/` |
| `.github/workflows/deploy-prose.yml` | push 到 `main`，且改动命中 `prose/**`、`technical/source/_posts/**`、`technical/source/_prose/**`、`technical/source/attachments/**` | 重建文苑 → `/var/www/blog/prose/` |
| `.github/workflows/deploy-terminal.yml` | push 到 `main`，且改动命中 `terminal/**` | → `/var/www/adaydream/` |

两条关键结论：

1. **只有 `main` 会部署。** 推到任何其它分支（例如 `draft`），GitHub 只存文件，服务器一动不动。
2. **`deploy.yml` 没有 paths 过滤。** 只要 push 到 `main`，哪怕只改了一个 README，
   也会整站重建并带 `--delete` 同步一次。所以「推 main」= 「发布」，没有中间态。

---

## 二、结论：可以实现，推荐「Syncthing + NetBird 同步，git 只做发布闸门」

两者分工，别混用：

- **Syncthing + NetBird** —— 负责 Mac ↔ Windows 的**文件同步**。完全不经过 git，
  因此**结构上不可能**触发部署。
- **git** —— 只负责**发布**和回滚。只在 Mac 上执行。

这样 Windows 就是一台纯粹的编辑终端，它没有能力让线上发生变化。

---

## 三、方案 A：Syncthing + NetBird（推荐）

### 3.1 装 NetBird

作用：给两台机器组一张私有 mesh 网，Syncthing 之间直连，不用打洞、走内网速度。

1. 在 NetBird 控制台拿到 setup key。
2. macOS：装 GUI 客户端（最省事），或
   `curl -fsSL https://pkgs.netbird.io/install.sh | sh`
3. Windows：下载官方安装包。
4. 连接：GUI 登录，或 `netbird up --setup-key <YOUR_SETUP_KEY>`。
5. 连上后每台机器会分到一个 `100.x.y.z` 地址，`netbird status` 可以看。
   参考：<https://docs.netbird.io/get-started>

### 3.2 装 Syncthing

- macOS：`brew install --cask syncthing`（菜单栏版），或
  `brew install syncthing && brew services start syncthing`
- Windows：推荐 SyncTrayzor（自带托盘与开机自启）。
- 管理界面：<http://127.0.0.1:8384>
- 默认端口：`22000` TCP/QUIC（同步数据）、`21027` UDP（局域网发现）、`8384`（本机 GUI，只监听 127.0.0.1）。
  参考：<https://docs.syncthing.net/intro/getting-started.html>

### 3.3 配对

1. 两边 GUI → **Actions → Show ID**，互相添加设备。
2. 同一张 NetBird 网里，设备地址可以直接填 `<对端 100.x.y.z>:22000`，不必依赖发现服务。
3. Mac 端添加文件夹：路径 `/Users/mac/Downloads/Blog`，Folder ID 例如 `obsidian-blog`，
   类型 **Send & Receive**。
4. Windows 端接受共享，本地路径例如 `D:\Obsidian\Blog`。
5. **顺序很重要**：先在 Mac 端把 `.stignore` 写好，再共享给 Windows。

### 3.4 `.stignore`（关键，别省）

放在被同步文件夹根目录（`/Users/mac/Downloads/Blog/.stignore`）。
语法要点：一行一个模式，`//` 开头是注释，`!` 前缀表示「不忽略」，
`(?d)` 前缀允许 Syncthing 删掉阻挡目录删除的系统文件。

```
// ================= 绝对不要同步 .git =================
.git
.git/**

// ================= 依赖与构建产物 =================
node_modules
**/node_modules
technical/public
prose/dist
.cache
.local

// ================= Obsidian 的易变状态 =================
// workspace.json 会随窗口布局频繁变动，同步它只会制造噪音和冲突
.obsidian/workspace.json
.obsidian/workspace-mobile.json

// ================= 系统垃圾文件 =================
(?d).DS_Store
(?d)Thumbs.db
(?d)desktop.ini

// ================= Syncthing / Obsidian 自己的目录 =================
.stversions
**/.stversions
.trash
```

**为什么 `.git` 必须排除：**
Syncthing 不懂 git，它会把 `.git/objects`、`.git/index`、`refs` 全部当普通文件搬运。
只要有一台机器正在 `git commit`（写 index 和 objects），同时另一台也在跑 git，
两边就会互相覆盖内部文件，最坏的情况是仓库损坏。而且 `.git` 里文件碎、变更频繁，
同步开销也大。

排除之后，Windows 上就是一个**没有 git 的普通 Obsidian 目录**，git 只存在于 Mac。
这正是「Windows 不可能误触发部署」的根本原因。

### 3.5 日常流程

```
Windows Obsidian 写作
      ↓ Syncthing 自动同步（秒级）
Mac 的工作区出现改动
      ↓
在 Mac 上 git status / 让 agent 提交
      ↓
想发布  → git push origin main      （触发部署）
不想发布 → 什么都不做，或推到 draft  （不触发任何 CI）
```

### 3.6 两个必看的坑

- **Syncthing 不做内容合并。** 同一篇在两台机器同时改，会产生
  `xxx.sync-conflict-20260926-120000-ABCDEF.md` 这种命名的新文件，不会自动合并。
  约定「同一时间只有一台机器改同一篇」；发现 conflict 文件就手动合并后删掉。
- **不要把库放在会被 OneDrive / iCloud 接管的目录。** 它们的「按需下载」会把文件变成
  占位符，Syncthing 会读到 0 字节或反复重扫。Windows 上请用 `D:\Obsidian\Blog`
  这类纯本地路径。

## 四、方案 B：git 分支（`draft`）

如果不想装 Syncthing，用分支也能做到「同步但不发布」。远端已经建好 `draft` 分支：

```bash
git switch draft      # 两台机器都切到草稿线
# 正常编辑、commit、push origin draft —— 不会触发任何工作流
```

想发布时：

```bash
git switch main
git merge draft
git push origin main   # 这一步才会部署
```

已实测确认：推 `draft` 不会产生任何 Actions 运行记录，因为三条工作流都只监听 `main`。

Windows 端要用 git 的话：

1. 装 Git for Windows（含 Git Credential Manager）。
2. `git clone https://github.com/Blooming-cherry/Blog.git`
3. `git switch draft`
4. Obsidian 装社区插件 **Git**（`Vinzent03/obsidian-git`），设置成定时 auto pull /
   commit-and-sync。

注意 `.obsidian/` 被 `.gitignore` 排除，所以插件设置、主题、快捷键**不会**同步，
两台机器各配一次。

> **方案 A 和方案 B 不要混用。** 一旦用 Syncthing 同步了同一个目录，
> Windows 侧就没有自己的 `.git`，也就无法 push —— 这时候再在 Windows 上跑 git
> 只会制造一个分叉的仓库。

## 五、补充：`[skip ci]`

如果某次必须直接推 `main` 又不想部署，可以在提交信息里带 `[skip ci]`，
GitHub Actions 会跳过这次 push 的全部工作流：

```bash
git commit -m "docs: 整理笔记 [skip ci]"
```

但它是**临时的**：文件已经进了 `main`，下一次不带 `skip` 的 push 会把它一起构建发布。
所以它适合「临时避免重跑」，不适合当长期草稿箱 —— 长期草稿请用 `draft` 分支。

## 六、换行符

仓库根目录已有 `.gitattributes`：文本一律以 LF 入库、以 LF 检出；
`*.cmd` / `*.bat` 例外，保留 CRLF 给 `cmd.exe`。

这条对方案 A 尤其重要：Syncthing 是**按字节搬运**的，它不认 `.gitattributes`。
Windows 上的编辑器如果写 CRLF，同步到 Mac 后工作区就是 CRLF 文件；
但有了 `text=auto`，git 在比对和入库前会先归一化，
所以**不会**出现「只改一个标点却显示整篇被替换」的假 diff。

仍建议把 Windows 端编辑器设成保存 LF（Obsidian 默认就是 LF；
VS Code 设 `"files.eol": "\n"`），减少无谓的同步往返。

## 七、怎么确认「确实没上线」

```bash
gh run list --limit 5      # 本地有 gh 的话
```

或者直接看 <https://github.com/Blooming-cherry/Blog/actions>。
判据：最近一次运行对应的 commit 是不是你以为要发布的那次。
只推了 `draft` 的话，列表里不会出现新的运行记录。
